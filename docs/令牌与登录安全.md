# 令牌与登录安全设计

本文说明本程序如何处理 **EVE SSO 登录、角色关联、令牌刷新与加密存储**，
以及每条设计取舍的理由。

设计参考了 [natemsz/evesynapse](https://github.com/natemsz/evesynapse)（Go）的
`auth.go` / `auth_links.go` / `auth_refresh.go` / `auth_tokencrypt.go`。
凡是与它不同的地方，下面都会写明**为什么不同**。

---

## 一、威胁模型：本地工具和在线服务不一样

EveSynapse 是一个多租户在线服务，它的敌人是「互联网上随便什么人」，
所以要防账户接管、防越权访问他人角色、防爬。

本程序是**跑在你自己电脑上的单用户工具**，敌人是另外三类：

| 威胁 | 具体形态 | 本程序的应对 |
|---|---|---|
| **本地文件泄露** | `data/` 目录被同步到网盘、被打包发出去、被别的程序读到 | 令牌加密落盘（见第三节） |
| **网页替你发请求** | 你访问的恶意页面通过 `fetch` 向 `127.0.0.1:8420` 发请求 | Origin 校验（见第五节） |
| **DNS rebinding** | 攻击者的域名解析到 `127.0.0.1`，浏览器就以为请求是同源的 | Host 校验（见第五节） |

「账户接管」在本程序里不成立（只有一个用户），但**角色被转手**这件事仍然重要：
你买的角色可能带着前主人的痕迹，反过来你卖掉的角色也不该继续用你的授权。

## 二、登录流程

```
点「登录 EVE」
  → POST /api/auth/login：生成 state(24 随机字节) + PKCE S256(32 随机字节)
     存入进程内待处理表（10 分钟过期，用掉即删）
  → 浏览器**同标签页**跳转 login.eveonline.com（不用弹窗：await 之后
     window.open 已脱离用户手势，会被浏览器静默拦截）
  → 你在 CCP 页面点 AUTHORIZE
  → 回调 http://localhost:端口/callback?code=…&state=…
     ① state 必须存在、未用过、对得上（对不上直接拒绝）
     ② 用 code + code_verifier 换令牌（公共客户端，无需 secret）
     ③ **验签**：RS256 + JWKS，校验 iss（两种写法都接受）、exp、
        aud（必须同时含本应用 client_id 与 "EVE Online"）、sub 格式
        —— 验签失败就拒绝登录，**绝不退回到未验签的身份**
     ④ 落库 + 解密后的令牌只在内存里传给 ESI
```

### 与 evesynapse 的差异

| 项 | evesynapse | 本程序 | 理由 |
|---|---|---|---|
| PKCE | 没用（它是机密客户端，有 client_secret） | **用**（S256） | 本程序是公共客户端，没有 secret；PKCE 让「授权码被截获」也无用 |
| state 存储 | 服务端 session（30 天） | 进程内待处理表（10 分钟） | 本地应用没有 session 层；10 分钟足够走完授权，且窗口更小 |
| 登录入口 | 完整 Web 会话 + cookie | 无会话（服务只监听本机） | 单机单用户，会话机制带来的复杂度大于收益 |
| 错误展示 | 8 个短码 + 首页友好文案 | 中文错误文案（已剥离 HTML、不含令牌值） | 面向本机使用者，直白比隐藏更有用 |

**JWKS 的 key 轮换**：拿到的 JWT 的 `kid` 不在缓存里时，会**强制重取一次 JWKS**
再验签；仍然失败才拒绝。这样 CCP 换签名密钥时不会导致登录失败。

## 三、令牌加密存储

### 信封格式

```
DPAPI1\0 + 密文                  Windows DPAPI（默认）
enc:v2: + base64(nonce‖密文‖标签)  AES-256-GCM（跨平台）
PLAIN1\0 + 明文                   兜底（仅在后端都不可用时，界面会告警）
```

读取时**按前缀分派**，所以换过后端仍能解开旧数据。

### AES-256-GCM 的参数（与 evesynapse 对齐）

| 项 | 值 |
|---|---|
| 算法 | AES-256-GCM |
| 密钥 | HKDF-SHA256(口令, 固定盐, 固定 info) → 32 字节 |
| 盐 / info | `eve-industry token encryption salt` / `eve-industry/token-encryption/v2` |
| nonce | 12 字节，每次**随机**（`os.urandom`） |
| 布局 | `nonce(12) ‖ 密文 ‖ 标签(16)`，不分隔 |
| AAD | `character:<角色ID>:<access\|refresh>` |
| 口令来源 | 环境变量 `EVE_TOKEN_ENCRYPTION_KEY`（≥32 字符），否则 `data/token.key`（自动生成 64 位十六进制） |

**AAD 绑定是最容易漏掉、也最有价值的一条**：它把密文钉死在「哪一行、哪一列」上。
把 A 角色的刷新令牌复制到 B 角色行、或者把 refresh 的密文塞进 access 列，
都会因为 AAD 不匹配而解不开。测试里专门验证了这两种搬用都必须失败。

Windows 上的 DPAPI 后端把同一串 AAD 混进 DPAPI 的附加熵，
所以两种后端获得**同等的行列绑定**。

### 为什么 Python 标准库没有 AES、却仍然能加密

本项目的原则是「零第三方依赖」，而 Python 标准库不提供任何分组密码。
所以 `app/aesgcm.py` 自己实现了 AES-256 与 GCM 所需的 GHASH：

* S 盒**按定义现算**（GF(2⁸) 求逆 + 仿射变换），不抄 256 字节的表 —— 抄错一个字节很难发现，现算反而可靠。
* GHASH 用逐位乘法，慢但代码短、易审查；令牌只有几百字节，性能无所谓。

正确性不靠「看起来对」：

* FIPS-197 附录 C.3 的 AES-256 官方向量
* RFC 5869 附录 A.1 的 HKDF-SHA-256 向量
* **与 Node 内置 `crypto` 的随机差分对拍**（AES 单分组 / GCM 多长度 / HKDF）

> 开发过程中这里真的出过一次错：`AddRoundKey` 的行列下标写反了，代码读起来毫无问题，
> 但 FIPS 向量立刻不对。这就是为什么要拿外部实现做对拍，而不是只信任自己的实现。

### 启动迁移

启动时会把明文/旧信封的令牌**就地**换成当前后端，并保证：

* **幂等**：已经是当前格式的行逐字节不动
* **不静默**：解不开的行（换了机器、丢了密钥）会被标成「需重新登录」，
  并在「关于 → 环境自检」里报出来；绝不会悄悄当成空令牌

与 evesynapse 的差异：**它解不开就拒绝启动**。本程序不这么做 ——
常驻服务拒绝启动是对的，而桌面工具起不来比带着告警运行更糟。
所以改成「标出问题角色 + 继续运行 + 明确告警」。

## 四、角色关联与所有权

### `link_state`：三种状态

| 状态 | 含义 | 后果 |
|---|---|---|
| `ok`（或旧行的空值） | 正常 | 允许同步 |
| `owner_changed` | **角色换了主人** | 暂停同步，等重新登录或点「确认已转手」 |
| `token_dead` | EVE 明确拒绝了这组令牌 | 暂停同步，等重新登录 |

暂停的含义是**不拉数据、也不拿它的令牌发任何请求** —— 这一点有测试覆盖。

### owner_hash：角色的产权凭证

EVE 的 `owner` claim 会随角色转手而变。规则：

* 两侧**都非空**且不同 → 判定为换主人 → 打 `owner_changed`
* 任一侧为空 → **不**判定（CCP 偶尔不给这个 claim），且**绝不用空值覆盖已知值**

登录时如果发现换主人，仍然会存入新的 hash，但状态是 `owner_changed`：
再登录一次（此时 hash 已一致）或点一下「确认已转手」即可恢复。
这样处理是因为**旧主人的缓存数据不该被新主人当成自己的**。

### 与 evesynapse 的差异

它是多账户服务，所以「同一个角色被两个账号关联」时**最新登录者获胜**，
角色会从一个账号搬到另一个账号。本程序只有一个用户，没有「搬到哪个账号」的问题，
所以只保留**所有权变更检测**这一条，把它变成「暂停 + 让用户确认」。

## 五、本机请求来源校验

这个服务没有任何登录态 —— 任何能访问 `127.0.0.1:8420` 的程序都能读你的 ESI 数据。
所以加了两道闸门（每一道都有测试）：

1. **Host 必须是 `localhost` / `127.0.0.1` / `[::1]`**
   防 **DNS rebinding**：攻击者把自己的域名解析到 127.0.0.1，
   浏览器就认为请求是同源的，于是能**读到返回内容**。挡住 Host 就没这回事了。

2. **带 `Origin` 头的请求，Origin 必须正好是本机这个端口**
   防 **CSRF**：你打开的恶意页面替你向本程序发请求。
   `Origin: null`（沙箱 iframe、`file://`）一律拒绝。
   **没有** `Origin` 头的请求放行 —— 否则 curl、PowerShell、本机脚本都没法用。

跨源预检（OPTIONS）同样拒绝。浏览器顶层导航（比如从 CCP 跳回 `/callback`）
不带 Origin，因此不受影响。

## 六、令牌刷新

```
取令牌 → 内存缓存（距过期 > 60 秒直接用）
       → 数据库里的访问令牌（锁内重读）
       → 用刷新令牌向 CCP 换新的
```

* **提前量 60 秒**（与 evesynapse 一致）
* **按角色串行**：同一个角色的刷新走同一把锁，不同角色互不阻塞
* **锁内重读数据库**：另一个线程可能刚刷完，直接复用即可

为什么必须串行：**EVE 每次刷新都会轮换 refresh token**。
两个线程拿着同一个旧 token 去换，后写回的那个会把先写回的作废 ——
表现就是「偶尔莫名需要重新登录」。这是修之前真实存在的 bug，
`tests/test_tokens.py` 里用 8 个线程验证「只允许刷新一次」。

### 失败分类：什么该标记、什么不该

| 失败 | 判定 | 处理 |
|---|---|---|
| `invalid_grant` / `invalid_token` | **确定性**：EVE 明确拒绝 | 标记 `token_dead`，停止重试 |
| 网络不通 / CCP 5xx | 暂时性 | 不标记，下次再试 |
| HTTP 401（client_id 可能配错） | 配置问题 | **不标记** |
| 解不开密文 | 配置问题 | 不标记，报出来 |

> 与 evesynapse 的差异：它把 ESI 401 也算确定性失败。
> 本程序不算 —— 对单机工具而言「client_id 填错了」是很可能的原因，
> 不该因此把用户有效的授权记录清掉。这个差异是有意的，代码里有注释说明。

### ESI 限流

| 状态 | 含义 | 处理 |
|---|---|---|
| **420** | 应用级错误预算被打穿 | **停止全部请求**，不重试 |
| **429** | 只有**这个角色**的速率预算耗尽 | 只停该角色；`Retry-After` 上限 15 分钟，只延长不缩短 |
| `X-ESI-Error-Limit-Remain ≤ 5` | 预算见底 | 主动减速（提前退让，而不是等 420 砸下来） |
| `X-Ratelimit-Remaining < 20` | 速率余量低 | 放慢到每 0.5 秒一次 |

重试只针对 **GET / HEAD**：重复 POST 可能造成重复副作用，宁可失败。
5xx 重试退避 0.5s → 1s（`Retry-After` 上限 10 秒）。
响应体有 8 MiB 上限，避免异常响应把内存吃满。

## 十、请求哪些权限（scope）：分层 + 审计

### 分两档，按需请求

参考站点（ceve-industry.cn）的授权入口有**两个按钮**：「仅授权人物信息」与
「授权人物+军团信息」—— 两档请求的 scope 数量不同。本程序照此实现：

| 档位 | 数量 | 内容 |
|---|---|---|
| **只授权个人数据** | 8 项 | 个人工业项目、个人蓝图、个人资产、**解析玩家建筑名**、自己在军团里的职位、技能、当前位置、个人市场订单 |
| **个人 + 军团数据**（默认） | 13 项 | 上面全部，加上军团工业项目、军团蓝图、军团资产、军团建筑、军团部门 |

登录弹窗里可以选。选个人档之后，军团相关页面会显示一条可操作的提示
（不是报错），点一下就能**追加**军团授权 —— 重走一次 SSO 即可，个人数据不受影响。

> 应用注册时仍要把 13 项**全部勾上**：EVE SSO 按应用登记的 scope 校验，
> 请求未登记过的 scope 会以 `invalid_scope` 拒绝。分层只是「登录时少要一点」，
> 不是「注册时少勾一点」。

### 为什么这很重要：一个反面样本

网络上流传的某个 EVE 工具的授权链接一次请求了 **59 项**权限。用本程序的审计函数
跑一遍，其中 **6 项是「能代替你做事」的**：

| 高危 scope | 它能做什么 |
|---|---|
| `esi-mail.send_mail.v1` | **以你的名义发邮件** |
| `esi-mail.organize_mail.v1` | 删除 / 移动你的邮件 |
| `esi-ui.open_window.v1` | 在你的游戏客户端里打开窗口 |
| `esi-ui.write_waypoint.v1` | 往你的自动导航里写路径点 |
| `esi-fleets.write_fleet.v1` | 改组你的舰队 |
| `esi-planets.manage_planets.v1` | 改你的行星工厂 |

本程序**一项都不需要**。它只读四类数据：工业项目、蓝图、库存、技能
（外加建筑名与角色自身的位置/职位/订单）。

为此在代码里加了审计函数 `config.audit_scopes()`：

* 默认的两档权限**必须审计干净**（有单元测试钉住，包括拿上面那份 59 项的真实
  授权链接当反面样本，验证它确实能被挑出 6 项）
* `config.json` 允许自定义 `scopes`；一旦混进高危权限，
  **登录时会打日志告警**，「设置」页也会显示醒目提示
* 触发词参考 evesynapse 的剔除规则：`send_` / `write_` / `respond_` /
  `organize_` / `manage_` / `open_window`

### 登录链接是「点一下自动跳过去」

不需要用户复制任何链接：点「登录 EVE」→ 选档位 → 点「前往 EVE 授权页面」，
浏览器**在同一个标签页直接跳到** `login.eveonline.com`（不用弹窗，
所以不会被浏览器的弹窗拦截拦掉）。授权完成后 CCP 把浏览器送回本机
`/callback`，程序自动换令牌并开始拉数据。

### 等待窗口：把手动兜底放在用户一定会看到的地方

点完授权之后用户就被带到 EVE 页面了。**如果回调没能回到本机**
（端口被占、换了浏览器、回调地址被拒…），他切回本程序时看到的是一个
安静的界面 —— 根本不知道去哪手动粘贴。

所以只要服务端还有未完成的登录尝试，启动时就会弹出**等待窗口**：

```
正在等待角色通过 EVE 登录
  · 本次请求权限    8 项
  · 回调地址        http://localhost:8420/callback
  · 还有效          约 9 分钟
  [重新打开授权页]                    [取消这次登录]

授权页打不开 / 回调被拒？
  ┌────────────────────────────────────────────┐
  │ 把浏览器地址栏里那一整条 URL 贴到这里…        │
  └────────────────────────────────────────────┘
  [提交授权码]
```

窗口每 3 秒检查一次：一旦发现角色已加上（含在另一个标签页/另一个浏览器里完成的
情况），就自动关掉并开始拉数据；如果待处理的尝试消失（取消或过期）也会自动关掉。

> 对照 PyFA 的登录窗口：它显示「正在等待角色通过 EVE 登录」+
> 「If auto-login fails, copy and paste the token provided by pyfa.io」，
> 也就是**通过 pyfa.io 这个第三方中继**拿令牌再手动粘贴。
> 本程序的做法是「本机回调 + 等待窗口里的手动粘贴」，**不需要任何第三方中继**：
> 授权码只在你、CCP 和本机之间流转。这样少一个能看到你授权码的中间方。

### 一些同类工具的授权链接（对比记录）

| 做法 | 评价 |
|---|---|
| `redirect_uri` 指向自己的网站 + 哈希路由（如 `http://www.ceve-industry.cn/#/tranquilityCallback`） | 能用，但回跳后 SPA 拿交换结果比较绕；本程序用真实的本机路径更直接 |
| 手动粘贴**第三方中继给出的令牌**（PyFA 的 pyfa.io） | 多一个中间方；本程序只在本机换令牌 |
| 一次请求 59 项权限（含 6 项高危） | 见上节 |
| `state` 用 UUID v4（122 位熵） | 够用；本程序用 24 随机字节（192 位） |
| 不带 PKCE | 本程序带 PKCE S256：公共客户端没有 secret，PKCE 让授权码被截获也无用 |
| 带 `realm=ESI` / `device_id=<uuid>` | v2 SSO 已不需要（旧版遗留），本程序不发送多余字段 |

## 十一、已知限制

1. **本地单用户**：没有账户体系，所以不做登录限流 / 防爆破（没有可爆破的东西）。
2. **密钥与数据同目录**：`token.key` 和数据库都在 `data/` 下，
   拷贝整个目录的人两者都拿到。所以 **Windows 上默认用 DPAPI**
   （密文与当前 Windows 用户绑定，拷走目录也解不开）；
   只有想要「跨机器可迁移」时才改用 `token_encryption = "aes-gcm"`。
   无论哪种，都请勿把 `data/` 分享给别人。
3. **单进程假设**：刷新串行化靠进程内锁。本程序本来就是单进程工具。
4. **API 无鉴权**：只靠 Host/Origin 校验。如果本机上已经有恶意程序在跑，
   它能直接读数据库 —— 这不是本程序能防的。
